# Parameter initialization: proposed finite implementation contract

Read-only preparation, 2026-10-09. This proposal preserves every adopted mode of `pytorch.torch.nn.init.xavier_uniform_`: **xavier-uniform, seeded-repeat, kaiming-uniform, normal, zeros**. It does not freeze new interfaces, change accepted coverage or claim numerical probes. Current source/catalog and `TORCH_REMAINING_NINE_CLOSURE_REVIEW_20261009.md` were reviewed; no implementation, tests, build or native operation was started.

## Consumer and typed recipe

Recommend one initialization control recipe attached to Train, with a qualified source address and a separate ordered owner selection. It is not a tensor-forward node or a new model layer. Absence preserves native constructor defaults and every existing checkpoint/export byte contract. The inspector presents “Starting settings”, selected learned arrays, algorithm and only applicable controls; parameter/bias names remain visible. Reuse shared typed field templates and Information accordion.

Proposed wire value is versioned and bounded to 32,768 UTF-8 bytes:

```text
{schemaVersion:1, configurationVersion:1, componentID:"initialization",
 config:{seed:42, rules:[{owner:{node:<qualified model address>,parameter:<native local parameter name>},
                        algorithm:<enum>, settings:<algorithm-specific exact object>}]}}
```

`rules` has 1…128 unique exact owners and a deterministic canonical order by qualified address then native parameter name. No regex/wildcards, implicit “all weights”, duplicate overlapping groups or user executable callbacks. Resolve names from actual native learned parameter ownership after lazy materialization, not `state_dict` alone: running means/variances/counters are buffers and ineligible. Shared aliases, if later exposed, resolve to a single underlying owner and cannot receive conflicting rules. Scalar/vector parameters may select normal/zeros; fan rules require rank≥2. Bias is a separate selectable owner, never accidentally subjected to a weight rule. Supported production dtype is dense float32 CPU/MPS; CPU float64 is permitted only for independent lesson evaluation.

| Algorithm | Exact settings/defaults | Proposed finite validation |
|---|---|---|
| `xavier_uniform` | `{gain:1.0}` | finite gain 0…100 |
| `kaiming_uniform` | `{a:0.0,mode:"fan_in",nonlinearity:"leaky_relu"}` | finite a 0…100; mode fan_in/fan_out; nonlinearity relu/leaky_relu |
| `normal` | `{mean:0.0,std:1.0}` | mean −1e6…1e6; std 0…1e6 |
| `zeros` | `{}` | no numeric fields |

Seed is an exact non-Boolean integer 0…2^63−1. All real controls reject Boolean, nonfinite and nonzero float32 underflow/overflow. Unknown fields, wrong algorithm-specific fields, stale/nonlearned owners and unmaterialized shapes refuse before mutation. Fan-in/out use native tensor storage convention: dimension 1/0 multiplied by the remaining receptive-field dimensions, with no automatic transpose. Display this explicitly for transposed-convolution/custom-shaped owners so a familiar layer label cannot silently alter native semantics. Degenerate zero fan dimensions refuse. Zero gain/std are deliberate constant initialization and remain valid.

Reuse the current 200,000 model-parameter ceiling and 100,000,000 tensor-element ceiling without expansion. Check the complete selected owner plan and aggregate allocation before allocating random arrays or mutating any parameter. Temporary initialization storage must fit the existing admitted run budget; release it per owner. Validate every generated value finite before commit; mutation should be transactional or all candidate arrays should be validated before copying.

## Seed and lifecycle proposal

Recommend an explicit **CPU float32 initialization generator**, separate from the training RNG: derive each owner's seed from SHA256 of a version tag, user seed and stable qualified owner identity using canonical UTF-8 encoding; take the first eight bytes big-endian modulo 2^63. Construct a private CPU `torch.Generator`, apply the actual native `nn.init` function to that owner's CPU candidate tensor and copy to its actual training device under no-grad. This is declared initialization placement, not a silent CPU fallback for model execution. It avoids depending on MPS generator support and makes selected-owner values independent of rule iteration order and unrelated owner additions. Repeatability is promised within the pinned algorithm/version/Torch environment; cross-version random-stream stability is not promised. This choice needs root approval before probing/implementation.

Apply after all lazy shapes are materialized and before optimizer construction. Do not change parameter object identity or optimizer ordering. A fresh captured run applies the recipe once. Exact resume must restore saved model/training RNG/state and **must not apply initialization again**; bind the canonical initialization policy and resolved ordered owner identity into the explicit checkpoint contract so incompatible exact continuation refuses. Fine-tune restores all parent weights/buffers and does not reinitialize them even if an initialization policy is retained as provenance. An intentional reset is a separate confirmed fresh-run capture: invalidates any selected continuation mode/parent training-state reuse, clears stale run/output/cache evidence and starts fresh optimizer/scheduler/epoch/RNG; immutable parent artifacts remain untouched. Never mutate a completed saved file in place.

Keep desired policy, actual application status and inherited historical policy distinct. Manifest provenance should record `applied` versus `restored`/`inherited`, canonical recipe, resolved owners/shapes/dtypes, seed-derivation version, generator placement and Torch version. No huge initialized-value arrays or individual derived seeds are necessary in routine logs. Saved model state is the authoritative realized array. Inference model export loads that state without reinitializing it; an optional standalone fresh-training helper reproduces the policy using Torch+stdlib only and retains native parameter names/order.

## Exact existing integration seams

- `runner/engine.py`: `run` currently seeds and constructs/materializes a model in both explicit-optimizer and legacy branches (around 1059–1085). One shared post-materialization hook must serve both, without double application or applying before restore. Native GraphModel ownership and `export_model` are reusable; new helper code should remain isolated.
- `runner/checkpoint_lifecycle.py`: `contract` already binds semantic graph, ordered native ownership, seed, runtime and explicit optimizer/scheduler/objective state. Add initialization identity only when selected; `load` must preserve exact/fine-tune distinctions and old absent-policy semantics.
- `WorkflowCompiler.swift`: compiled plan already carries qualified optimizer/scheduler/loss recipes and Train control connections. Add one typed recipe/owner resolution through the same source-pinned capture pipeline, not free text in global settings. New configuration/recipe Core files plus narrow compiler/control declaration changes; preserve legacy workflow migration.
- App: shared inspector templates, actual runtime-discovered readiness, request/archive capture, provenance/History and existing reset/confirmation actions. Root should assign one owner for lifecycle/native verification and one for runtime changes; do not overlap frozen engine ownership.
- Bundle authoring/generation: one control bundle, exact optional discovered descriptor (algorithms, ownership/timing/seed/limits policies) and original themed generated icon. Generator publishes config/discovery only; no forward adapter or invented tensor ports.
- Standalone CLI/authorization: bounded canonical recipe plus captured qualified ownership; verify recipe/file/source pins before launch. An unrequested initializer flag is refused in preview/nontraining modes. Exports, captured registry and cold History retain the original selected recipe rather than using today's registry.

## Independent tests and finite exits

1. **Xavier:** independently compute fan_in/fan_out and bound `gain*sqrt(6/(fan_in+fan_out))` for rectangular affine and spatial weights, nondefault gain and zero gain. Actual native initialized values must lie within bounds. Seeded samples use deterministic predeclared mean/variance tolerances over several fixed seeds/large-enough bounded arrays, not a brittle one-value distribution assertion.
2. **Kaiming:** independently compute gain sqrt(2/(1+a²)) for leaky_relu or sqrt(2) for relu, selected fan and bound sqrt(3)*gain/sqrt(fan). Exercise both fan modes, nondefault slope, rectangular shapes and rank refusal. Test native treatment of `a` with relu honestly; the inspector may explain that slope affects leaky_relu only.
3. **Normal/zeros:** independent expected constant results for zero std/zeros, nondefault signed mean and positive spread; bounded seeded distribution checks and exact zeros. All four native algorithms execute, not aliases to one random function.
4. **Seeded-repeat:** identical same-runtime recipe/owner yields identical arrays; changed seed changes stochastic arrays; reordered rule list and an unrelated additional owner do not alter existing selected arrays. Training RNG is unchanged by initializer application. CPU/MPS realized initialization matches the declared CPU placement policy; subsequent real forward/backward/training executes on the chosen device.
5. **Ownership/lifecycle:** every selected native parameter affected and unselected parameters/buffers unchanged; nested-qualified owners/lazy shapes/invalid owner rollback; exact restore bitwise continuation, fine-tune preserves loaded values, explicit reset starts new state. Invalid recipe/seed/type/rank/stale owner/aggregate budget fails before mutation. Independent affine predictions and first SGD update demonstrate realized starting values affect actual computation.
6. **Persistence/export:** actual fresh-run policy capture → completed History → cold read → portable learned-state inference and standalone seeded fresh-training helper without app imports. Compare independent predictions, owner ordering and realized arrays. Tampered policy/state/source pins, unsupported generator/version and oversized artifacts refuse. Prior absent-policy checkpoints/contracts and generated families stay unchanged.

Closure requires all five adopted modes, two paired lessons/examples and original icon, exact discovery/admission, current-source regression, actual root-owned CPU/MPS/native capture/History/export evidence, and frozen per-mode bindings. No default constructor behavior alone closes this unit.

## Two approachable lesson tasks

- **“Choose starting settings.”** Define learned settings as numbers the model will adjust, and seed as a repeatable starting-number choice. On a small two-column prediction flow, select Normal for one weight array and Zeros for its bias; compare actual predicted values and one learning step. Guided instructions define spread in plain language. Practice/private/cold cases change input values, seed and mean/spread. Grade actual initialized arrays, selected/unselected ownership, predictions and repeatability—never merely a menu selection.
- **“Match the starting spread to a layer.”** Explain that more incoming values can make totals grow, then choose Xavier or Kaiming with different incoming/outgoing widths and a visible ReLU/LeakyReLU. Teach the native stored weight directions visually, optional high-school square-root formula in Information. Grade independently bounded starting values, the actual chosen fan/gain/slope effect, seeded repetition and output influence. Include both algorithms through paired checkpoints/variants, with valid wrong controls measurably failing. No claim that one initialization guarantees training success.

## Decisions to resolve before implementation

Root must approve: (1) the typed recipe control/source spelling and owner selection schema; (2) private per-owner CPU generator placement/seed derivation versus a device-local alternative; (3) exact numeric/selection limits above; (4) whether explicit reset is a new fresh-run action or an existing confirmed action; (5) exact optional discovery descriptor and initialization identity/provenance fields, especially fine-tune inherited policy versus selected policy. These are finite interface choices, not permission to reduce algorithms/modes. Installed native CPU/MPS support and generator behavior must be probed after those decisions, with unsupported behavior reported rather than silently narrowed.

## Root-frozen implementation boundary · 2026-10-09

All five adopted modes remain required. Implement `initialization` as one connected control recipe, never a tensor-forward operator. The authored configuration is `{seed:<Int64 0...2^63-1>,rules:[{owner:{node:<expanded model node ID>,parameter:<native parameter name relative to that node's module>},algorithm:<xavier_uniform|kaiming_uniform|normal|zeros>,settings:<exact applicable object>}]}`. Workflow compilation resolves the selected model snapshot and validates selected node identities against its captured graph/origins; labels show the original Block path where present. Worker resolution uses that node's actual module and native `named_parameters()`; do not infer owners from `state_dict` or concatenate unvalidated user source code. Nested parameter names are allowed only when actually present. Canonical ordering is owner.node then owner.parameter. No arbitrary strings for module lookup outside the selected model, duplicate owners or overlapping native parameter identities.

The wire recipe is the version1 envelope proposed above. Choose the documented private per-owner CPU float32 generator and SHA256 seed derivation, with canonical JSON `["kwip.initialization.owner-seed.v1",seed,node,parameter]`, UTF-8, sorted keys/compact separators, first8 digest bytes big-endian modulo2^63. Copy to the actual CPU/MPS device under no-grad; training still executes on its selected device. Exact limits/settings in the proposal are adopted. Generate and validate all selected candidate arrays before any copy; their aggregate is bounded by the existing200,000 total model-parameter limit, plus existing admitted work budgets. Do not loosen global ceilings.

Initialization applies once on fresh runs, after lazy materialization and before optimizer creation. Resume/fine-tune never apply it to restored weights. Bind canonical selected recipe and resolved ownership/shapes/dtypes as an optional initialization checkpoint field only when selected. Existing absent-policy contracts/exports retain their exact semantics. Fine-tune records inherited/retained policy distinctly from newly applied state. An intentional reset uses the existing explicitly selected Start fresh training mode with its normal new-run capture; do not add an automatic reset, rewrite a parent or claim an interactive in-place reset. Existing source/revision/capture invalidation remains authoritative.

Use schema9 and compiler contract8 for the new workflow initializationRecipe payload/edge/optional Train.initialization port, preserving old decode and unsupported-version refusal. The exact discovery descriptor will be frozen jointly from the independently tested helper before publication. Source-pinned request transport must use the existing recipe capture and authorization pattern; no ad hoc mutable file argument. Runtime foundation and typed Core configuration may develop in parallel in new owned files; shared engine/Workflow changes receive explicit leases after their tests prove these interfaces. No catalog credit until full application/lesson/export/artwork/native acceptance.

### Frozen discovery and persisted metadata

Runtime discovery adds only `initializationCapabilities.initialization` with literal descriptor:

```json
{"version":{"major":1,"minor":0,"patch":0},"adapterID":"kwip.runner.initialization","recipeSchemaVersions":[1],"configurationVersions":[1],"algorithms":["xavier_uniform","kaiming_uniform","normal","zeros"],"seedMinimum":0,"seedMaximum":9223372036854775807,"seedDerivation":"kwip.initialization.owner-seed.v1","generatorPlacement":"cpu-float32","devices":["cpu","mps"],"parameterDTypes":["float32"],"maximumRecipeBytes":32768,"maximumRules":128,"maximumModelParameters":200000,"ownerPolicy":"expandedNodeRelativeNativeParameter","ownerOrder":"nodeThenParameter","aliasPolicy":"rejectDuplicateParameterIdentity","fanPolicy":"nativeStoredDimensions","applicationTiming":"freshAfterLazyBeforeOptimizer","restoredWeights":"preserve","candidateCommit":"validateAllBeforeCopy","preservesParameterIdentity":true,"initializesBuffers":false,"standaloneHelperMaximumBytes":131072}
```

Resolved owners are sorted `{node,parameter,name,shape,dtype}` entries, with full actual native `name`, float32 and positive actual stored shape. GraphModel.layer_keys is the authoritative collision-safe expanded-node→native key mapping. Do not assume the strings match or select buffers from state dictionaries.

Only a selected recipe adds `checkpoint.contract.initialization = {schemaVersion:1,recipe,resolvedOwners,generatorPlacement:"cpu-float32",seedDerivation:"kwip.initialization.owner-seed.v1"}`, `manifest.settings.initializationRecipe = recipe`, and `manifest.provenance.initialization = {schemaVersion:1,recipe,resolvedOwners,generatorPlacement,seedDerivation,torchVersion,application}`. Application is exactly `applied` on fresh execution or `notAppliedOnRestore` on exact resume/fine-tune. The recipe is the **selected desired fresh-start policy**, not a claim that restored weights came from that policy. Parent historical policy remains in immutable parent lineage. When target selection is absent, omit all new fields/artifact; fine-tuning a parent with a policy into an unselected target remains valid. Exact continuation requires matching optional-policy presence and identity. No extra top-level checkpoint tensor payload is needed.

Emit `initialization_recipe.py` only when selected, maximum131072bytes, through the existing atomic artifact mechanism. It contains the standalone strict Torch/stdlib helper and canonical selected recipe, never auto-applies on inference load. Existing `training_recipe.py`8192bytes and all other global/artifact limits remain unchanged. App artifact inventory/verifiers/export must bind the new helper exactly before publication. Core's portable byte allocator reserves two extra bytes per integral real algorithm scalar because Python spells integral floats with `.0`; the UTF-8 wire is bounded, without asserting identical serializer bytes across languages.
